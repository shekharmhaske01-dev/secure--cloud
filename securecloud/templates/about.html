How {{ app_name }} works

Architecture, encryption format and operational notes.

End-to-end flow

Upload

  1. Client selects a file; the browser shows name, size and estimated block count.
  2. The server stages the stream to disk, enforcing the maximum upload size.
  3. A random 256-bit DEK is generated for this file.
  4. The file is segmented into {{ human_size(block_size) }} blocks.
  5. Each block is encrypted: AES-256-GCM(DEK, nonce, block, AAD).
  6. Each ciphertext is stored as one object named by opaque id + block index.
  7. The DEK is wrapped with the KEK; only the wrapped key is persisted.
  8. Metadata is committed as complete only after every object is verified.

Download

  1. Session and file ownership are verified.
  2. The wrapped DEK is unwrapped in memory with the KEK.
  3. Blocks are fetched and ordered by verified block index.
  4. Every block is authenticated and decrypted (tampering aborts the download).
  5. The plaintext is written to a temporary file and its length is checked.
  6. The file is streamed to the browser with a sanitised name.
  7. The temporary plaintext file is deleted after the response.

Database tables

  • users — account, Argon2id hash, server-side session token.
  • stored_files — owner, filename, size, block size/count, lifecycle status.
  • encrypted_blocks — block index, object key, nonce, sizes, format version.
  • wrapped_keys — wrapped DEK, wrap nonce, KEK fingerprint.
  • storage_operations — upload/download/delete audit and error categories.
  • cleanup_jobs — recoverable object-cleanup work.

No plaintext content and no unwrapped key is ever written to the database.
